# EcoBudget Codebase Analysis

## Purpose and Scope

EcoBudget is a research prototype for task-sufficient web loading. Given a
question and an HTML page, it extracts page resources, ranks text passages by
their likely usefulness per byte, and compares full-page, fixed-budget, and
adaptive-loading strategies. The project also estimates transfer-related CO2e.

This document describes the repository as checked out on 2026-09-09. The
`teammate-1-ml-retriever/` directory is deliberately excluded from this
analysis, per project guidance.

There are two related but distinct backend paths:

1. The FastAPI demo path in `backend/main.py` uses `backend/scorer.py` directly.
2. The experiment path in `backend/experiment_runner.py` uses the newer
   `conditions.py`, `evidence.py`, `controller.py`, and `usefulness.py` stack.

They share parsing and QA utilities but do not currently share a single
controller or response shape. Treat them as parallel prototype generations,
not interchangeable entry points.

## System Architecture

```text
Browser UI
  |  GET benchmark.json and pages/pageN.html
  |  POST /run three times: normal, fixed, ecobudget
  v
FastAPI (main.py)
  |-- parse_resources() ----------------------> BeautifulSoup HTML extraction
  |-- rank_by_vpb() --------------------------> embeddings + extractive QA
  |-- find_best_answer_full_page() -----------> extractive QA over all text
  |-- log_decision() -------------------------> SQLite logs/experiment.db
  `-- fetch_rendered_html() for /run_live ----> Playwright Chromium

Batch evaluator (experiment_runner.py)
  |-- parse_resources() and rank_by_vpb()
  |-- run_normal(), run_fixed_eco()
  `-- run_ecobudget()
        |-- EcoBudgetController
        |-- EvidenceCoverageTracker
        `-- UsefulnessModel and estimate_co2e()
```

The API path has a fixed 2,000,000-byte cap for its `fixed` condition and a
0.55 confidence threshold for its `ecobudget` condition. The experiment path
instead evaluates fixed 10 KB, 25 KB, 50 KB, and 100 KB conditions, then uses
coverage-driven adaptive stopping. These are materially different experiments.

## Backend Module Reference

### `main.py`: Active HTTP Demo

Exports the FastAPI `app`, request models `RunRequest` and `LiveRunRequest`,
and the reusable `run_core(...)` function. `init_db()` runs at module import.

`run_core` parses the provided HTML and dispatches on `condition`:

| Condition | Selection behavior | Logged rows |
|---|---|---|
| `normal` | Delivers every extracted resource, including images; finds best QA answer over all text. | One summary row |
| `fixed` | Ranks up to 30 text resources by utility per byte and greedily fits them inside 2 MB. | One summary row |
| `ecobudget` | Delivers ranked text resources one at a time until utility reaches 0.55; otherwise falls back to all resources. | One row per initially loaded resource |

Any condition string other than exactly `normal` or `fixed` takes the
`ecobudget` branch. This is implementation behavior, not an enforced API enum.
The `ecobudget` log entries set `task_success` to `null`, even when a supplied
ground truth later determines a response-level success value.

Endpoints:

| Method and path | Input | Behavior |
|---|---|---|
| `POST /run` | `RunRequest` JSON | Runs one condition against caller-supplied HTML. |
| `POST /run_live` | `LiveRunRequest` JSON | Renders a URL with Chromium, then runs one condition. |
| `GET /logs` | None | Returns every SQLite log row, without pagination. |
| `GET /health` | None | Returns `{ "status": "ok" }`. |

The app enables unrestricted CORS for all origins, methods, and headers. It
does not mount or serve frontend files.

### `scorer.py`: Parsing, Ranking, and QA

This is the shared, active scoring layer.

| Public function | Input | Output and behavior |
|---|---|---|
| `extract_entities(text)` | String | Lowercased spaCy named-entity strings. |
| `extract_capitalized_terms(text)` | String | Capitalized phrase candidates after question-word filtering. |
| `entity_consistency_score(task, candidate)` | Two strings | `1.0`, `0.7`, or `0.3` entity-overlap heuristic. |
| `get_real_image_bytes(src, base_url)` | Image source and optional base URL | `(bytes, estimated)`; HEAD request when possible, otherwise `(50000, True)`. |
| `parse_resources(html, base_url, debug)` | HTML string | Resource dictionaries for infobox text, text blocks, and images. `debug` is unused. |
| `compute_utility(task, resource)` | Two strings | MiniLM cosine similarity as a float. |
| `check_answerability(task, text)` | Question and text passage | `(qa_score, answer_or_none)` from RoBERTa QA. |
| `rank_by_vpb(task, resources, use_entity_filter)` | Task and resource list | Mutates text resources with scores; returns at most 30 candidates sorted by utility per byte. |
| `find_best_answer_full_page(task, resources, use_entity_filter)` | Task and resource list | `(best_score, best_answer)` after QA over all text resources. |
| `check_task_success(answer, truth)` | Strings | Boolean string/word-set answer match. |
| `check_task_success_v2(answer, selected_text, truth)` | Answer, selected text, string or fact-set truth | `(success, facts_matched, facts_total)`. |
| `evidence_gate(...)` | Question, selected resources, QA answer/score | `(sufficient, reason)` heuristic gate. It is not called by the active API or evaluator. |

Parsing details: it prefers common Wikipedia content containers, removes
references/citations and layout tags, captures an infobox as one text resource,
adds nontrivial paragraphs/list items/headings, and includes images with a real
or estimated byte count. Ranking only considers text resources. In-place score
mutation means callers should not assume their original resource dictionaries
are unchanged after ranking.

### `db.py`: SQLite Logging

`DB_PATH` is `logs/experiment.db`, relative to the process directory. Exports:

| Function | Behavior |
|---|---|
| `init_db()` | Creates `logs/` and the `logs` table if missing. |
| `log_decision(entry)` | Inserts a mapping into the table; absent keys become `NULL`. |
| `get_all_logs()` | Returns all rows as dictionaries. |

Each operation opens, commits where needed, and closes its own connection. No
migration system, ordering, filtering, or transaction batching is provided.

### `fetch_live.py`: Live Webpage Acquisition

`fetch_rendered_html(url, wait_ms=2000)` starts headless Chromium, opens the
URL with a 15-second navigation timeout, waits a fixed duration for JavaScript,
and returns `page.content()`. Its command-line mode writes
`live_test_output.html`. It does not restrict destination URLs, retry requests,
or guarantee browser cleanup if an exception happens before explicit close.

### `conditions.py`: Experimental Conditions

Exports `select_within_budget`, `best_from_selected`, `run_normal`,
`run_fixed_eco`, and `run_ecobudget`. It is used by `experiment_runner.py`, not
by `main.py`.

* `run_normal` loads all resources and reports a carbon estimate.
* `run_fixed_eco` ranks text and greedily selects within a caller-selected
  budget (default 20,000 bytes).
* `run_ecobudget` reranks candidates, gives each a private `_cand_id`, uses the
  controller to choose a passage, updates evidence coverage, and stops based on
  coverage/caps/usefulness. It returns coverage and requirement detail.

This path disables the scorer entity filter for normal/fixed conditions but
enables it for adaptive ranking. Ground truth is intentionally not used in its
selection or stopping logic.

### `evidence.py`: Evidence Coverage Tracker

This is the active experimental tracker used by `conditions.py`. At import it
loads `google/flan-t5-base` and `all-MiniLM-L6-v2`.

For comparisons, Flan-T5 separately derives subjects and attributes, then the
module makes a subject-by-attribute requirement set. Other tasks get a single
requirement inferred from the question. A passage satisfies a requirement only
when it clears embedding similarity, an entity-presence check, QA confidence,
and an answer-shape regex check. `EvidenceCoverageTracker` maintains
requirements, byte/passages counters, coverage, answers, and a text status
report.

Key exported helpers are `extract_requirements`,
`passage_satisfies_requirement`, and the `EvidenceCoverageTracker` class.

### `controller.py`: Adaptive Selection Controller

`EcoBudgetController` owns a coverage tracker and a `UsefulnessModel`. It
builds feature vectors for every candidate, predicts usefulness, and sorts by
predicted usefulness per byte (`sel_score`). It stops when all requirements are
covered at threshold 1.0, candidate/load/budget limits apply, or predicted
usefulness falls below 0.05. `register_load` updates only controller counters;
the caller updates evidence separately.

Constructor parameters:

```text
EcoBudgetController(tracker, usefulness_model=None,
                    max_loads=15, min_useful=0.05, byte_budget=None)
```

The required tracker contract is `is_sufficient`, `frac_satisfied`,
`frac_remaining`, and `coverage`.

### `usefulness.py`: Feature Model

`FEATURE_NAMES` establishes the eight-feature training/prediction order:

```text
similarity, passage_size, value_per_byte, frac_satisfied,
frac_remaining, coverage, num_previous_loads, cumulative_bytes
```

`build_features(...)` returns this as a NumPy float array. `UsefulnessModel`
loads `models/usefulness.joblib` if it exists; otherwise `predict` returns a
clipped heuristic: `similarity * (0.5 + 0.5 * frac_remaining)`. `train(X, y)`
fits an `XGBClassifier` and persists it with joblib.

### `carbon.py`: Emissions Estimate

`estimate_co2e(total_bytes, green_host=False)` converts bytes to kWh using
`0.81e-9 kWh/byte`, then applies either 494 or 50 gCO2e/kWh. It returns a
mapping with raw bytes, kWh, host assumption, rounded grams, and an explicit
note that this is an estimate rather than measured emissions.

### `semantic_engine.py`: Unwired Alternative Evidence Engine

This module is not reached from the API or current runner. It loads Flan-T5,
MiniLM, and BART-MNLI at import. It provides:

* `decompose_task` for `subject | attribute | question | type` requirements.
* `rank_for_requirement` for per-requirement embedding ranking.
* `verify_passage` for NLI verification plus dynamic import of scorer QA.
* `SemanticCoverageTracker` for NLI-backed coverage, answers, and reporting.

Unlike `EvidenceCoverageTracker`, its requirement keys are `requirement` and
`answer_type`, and it does not expose `frac_satisfied`/`frac_remaining`.
Therefore it cannot be passed to the current `EcoBudgetController` without an
adapter.

`parse_resources` emits the following conceptual union. The image-only
`bytes_estimated` property is absent for text resources.

```json
{
  "oneOf": [
    {
      "type": "object",
      "required": ["type", "content", "bytes"],
      "properties": {
        "type": { "const": "text" },
        "content": { "type": "string" },
        "bytes": { "type": "integer", "minimum": 0 }
      }
    },
    {
      "type": "object",
      "required": ["type", "content", "bytes", "bytes_estimated"],
      "properties": {
        "type": { "const": "image" },
        "content": { "type": "string", "description": "Image alt text" },
```

`sel_score` fields to copies or candidate dictionaries.

`frontend/index.html` is a dependency-free static page. On load it fetches the
symlinked `benchmark.json`; after the user chooses a task it fetches the
symlinked fixture and posts it to `http://localhost:8000/run` three times.
The UI renders Normal, Fixed Eco, and EcoBudget cards, displays a success/fail
badge based on response `task_success`, and reports EcoBudget byte reduction.

The frontend `benchmark.json` and `pages` symlinks are relative and valid in
this checkout. In contrast, `backend/pages/pages` is an unused symlink to
`/Users/kasmyabhatia/ecobudget/backend/pages`, an absolute path from a
different machine. Nothing in the analyzed source reads that stale link.

## Important Development Boundaries

* The project has no automated tests or declared installation command. Before
  modifying selection behavior, exercise at least the relevant API endpoint or
  batch condition with a saved fixture.
* API success checking supports only string ground truth. The richer fact-set
  format is supported by `scorer.check_task_success_v2`, but that function is
  not called by `main.py` or the present batch runner.
* The experiment runner currently calls `check_task_success`, passing
  `t["ground_truth"]`. Structured ground-truth tasks in the frozen benchmark
  therefore need an integration update before this runner can handle them.
* The frontend needs a static server that follows symlinks, plus the FastAPI
  process on port 8000. FastAPI itself only serves API routes.
* Ranking is computationally expensive: `rank_by_vpb` computes an embedding
  for every text resource and runs extractive QA over the top 30 before sorting.
  Its image HEAD requests can also make parsing network-dependent when a base
  URL is supplied.
* The API and experimental adaptive paths have different thresholds, budgets,
  stopping mechanisms, logging behavior, and response contracts. Choose the
  intended path before changing a metric or presenting a result.
* The `.gitignore` ignores `__pycache__/` and `.DS_Store`, but generated Python
  bytecode is already tracked. Treat source `.py` files, not `.pyc` files, as
  authoritative.

## Suggested Agent Starting Points

For an API/demo task, start in `backend/main.py`, then follow calls into
`scorer.py` and `db.py`. For adaptive research behavior, start in
`backend/experiment_runner.py`, then read `conditions.py`, `controller.py`,
`evidence.py`, and `usefulness.py` in that order. For UI behavior, begin at
`frontend/index.html` and keep its legacy benchmark schema separate from the
structured benchmark schema.
